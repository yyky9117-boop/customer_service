# 手机号订单查询核验

核验日期：2026年10月9日。范围为手机号查询、候选选择、订单详情、模拟物流、账号边界和历史恢复，不代表推荐模块整体重新验收。

## 当前行为与本次修复

原订单模块已有手机号查询能力，本次没有替换原工作流的订单查询节点。之前界面主要展示订单号入口，分流也遗漏了“句子中只有号码、没有订单关键词”的输入。

现在两条路径为：

- 订单号 → 原参数规范化节点 → 独立订单数据库 → 原查询/渲染节点 → 客服话术与质检。
- 下单手机号 → 原格式核验节点 → 独立订单数据库按手机号筛选 → 多笔候选选择或唯一订单详情 → 同一详情与模拟物流链路。

数据源是相邻 `snack_customer_service/database/snack_orders_demo.sqlite`，用独立SQLite文件模拟接入的外部订单数据库。本轮未接入远程生产订单服务。连接为只读，SQL使用参数绑定，并同时按当前演示账号及手机号过滤；输入手机号不改变账号身份。

修复及补充：

1. 分流与抽取共用11位号码边界，支持直接发送号码或在句子中提供号码。
2. 数据库查询中加入手机号条件，不再先加载账号全部订单后仅在Python节点中筛选手机号。
3. 不同的多个手机号先澄清；同一号码重复出现按一个号码处理。
4. 错误手机号明确提示11位格式；新手机号查无记录不返回上一笔已选订单。
5. 共9笔、只展示最近5笔的候选回复补齐数量和展示范围说明。
6. 首页增加“用手机号找订单”；聊天框、欢迎语和演示说明明确支持手机号。

## 执行结果

- 全量自动检查247项通过，运行21.039秒，其中本次新增8项手机号与分流检查。包括真实演示订单库的9笔/最近5笔查询，以及独立临时库中的SQL手机号筛选、参数绑定与账号隔离。
- 真实网页使用16个检查点核对入口、句子内号码、9笔查询、5个选择按钮、待付款详情、列表外订单物流、已选订单追问、错误格式、纠正号码、多号码、查无记录、单笔订单、账号隔离、刷新恢复及手机布局。
- 浏览器检查全部通过，无脚本或CSP错误。浏览器实际发送10轮咨询。
- DeepSeek接口实际24次调用，供应商报告合计24,436 token，包含生成、质检及修复尝试；离线自动检查不调用模型。
- 9轮触发话术模型，其中8轮由生成和质检通过的模型话术返回；待付款详情1轮因话术产生无依据声明而被拦截，使用原事实话术兜底。多手机号澄清1轮不调用模型。格式错误提示由服务端固定说明覆盖。不能据此宣称模型每次生成都成功。
