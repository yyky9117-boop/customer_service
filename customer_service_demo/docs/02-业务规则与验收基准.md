# 第 2 步：演示数据、业务规则与验收基准

## 1. 本阶段的完成范围

本阶段建立固定数据、明确规则、数值基准和语义验收案例。没有运行推荐服务或模型，也没有实现网页。资产检查通过只说明数据、引用和基准算术一致；模型理解、推荐排序、故障恢复及并发仍须在第 3–5 步执行验收。

所有商品、用户、优惠券、活动均为虚构资料；不引用真实品牌，不把资料中的标签解释为真实产品认证。

固定时间为 **2026-10-07 12:00:00，Asia/Shanghai**。日期边界案例显式覆盖时间，不依赖测试当天的系统时钟。

文件：

- `data/products.json`：30 个商品，包含正常、缺货、未知字段、临期、过期及价格缺失样本。
- `data/users.json`：6 个演示身份，区分新客 / 老客、会员、持券状态和配送区域。
- `data/activities.json`：10 个活动，包含满减、百分比折扣、赠品、秒杀价、不完整规则与有效期边界。
- `data/coupons.json`：13 种券，包含品类范围、用户资格、持券、渠道、封顶和互斥条件。
- `data/manifest.json`：固定时间、运费政策、默认匿名身份和资源清单。
- `acceptance/fixtures.json`：只用于测试的局部数据覆盖与对抗内容。
- `acceptance/cases.json`：具有预期结果与失败条件的验收案例。
- `acceptance/pricing_goldens.json`：独立手算并可检查的固定购物方案数值基准。

## 2. 需求理解与状态更新

### N01：明确要求与偏好

“必须、不能、不要、最多、不超过”通常表示硬要求；“最好、优先、喜欢”通常表示偏好。最终以完整句义为准，不能只看单个词。

办公室等场景扩展出的便携 / 分享偏好是推测，不升格为硬要求。用户后来明确要求可改变其强度。每项条件保留原话、来源轮次和 explicit / inferred 来源；推测条件保存依赖来源，便于撤销。

### N02：否定、程度与纠正

“不辣”要求 `spice_level=none`；“不要太辣，但微辣可以”允许 none / mild，排除 hot。未知辣度不能满足明确辣度要求。“不是不能吃坚果，只是不喜欢花生”不等于排除所有坚果；“不喜欢花生”作为软偏好，除非用户补充明确排除。

“不甜”与“无糖”不同；无糖标签的薄荷糖仍可以有甜味。“苦味 / 黑巧 / 原味”不能推出低糖或无糖。

### N03：歧义与冲突

同组要求矛盾、预算单位 / 口径影响选择、指代不清、关键约束无法确认时追问。每轮最多问两个字段，避免重复问已知信息。“随便、不想回答”不触发无限追问；只要存在不违反已知硬要求的确定方案就可以继续。确实无法确认的必要条件不能靠猜测补齐。

### N04：预算

金额按分保存。“100 元以内”上限为 10000，严格；“100 元左右”目标为 10000，近似。近似预算不自动增加 20% 容忍区间，也不鼓励花满预算。超过近似目标的备选必须说明。

“50–100 元”的下界默认是偏好目标，不是必须花满 50 元；“至少花 50 元”才是硬下界，使用 `min_is_hard` 标记。

区分单件、单份 / 单人、商品合计和含运费整单。未说“含运费”时，可明确说明当前比较的是商品金额；如果运费会改变严格预算结论，必须澄清口径或给出商品价与含运费价两个数值，不宣称未知总价符合整单预算。

单件预算使用优惠分摊后的商品行金额与数量比较：`line_payable_fen <= unit_budget_fen * quantity`，不要把先四舍五入的均价用于门槛判断。

### N05：需求分组与共同预算

不同对象的口味、包装等约束单独保存。共同预算放在 `shared_budget`，不能给每个组各分配一遍总预算。“五份共 150 元”要核对五份合计；“每份 30 元，五份”同时核对单份与数量。

一个推荐方案是一个可购买选择；三个备选方案不是让用户把三份全部买下。共同订单内跨组费用必须合并计算，不能分组分别用掉同一张券。

### N06：多轮更新

“预算改成 60”只替换预算。“改成自己吃”撤销送礼条件以及依赖它推测出的礼盒偏好；如果礼盒是用户另行明确要求，则保留。新增条件不清除其他有效条件。

指代按稳定消息 / 方案 / SKU 标识解析。更换其中一个商品后要重新计算整个方案优惠，不能沿用原总价。重新开始对话后，不继承原需求、指代或未完成结果。

## 3. 检索和商品准入

### F01：基础可用性

确认推荐须有已知非负价格、确定且足够的库存、未过期状态。未知库存不等于有货。价格缺失、库存缺失、过期的商品不能成为已确认可购买方案。异常商品单独隔离，不因单条记录无效而把全库判断为无商品。

### F02：缺失字段与硬条件

必要字段未知时，不能判为满足硬条件；也不能编造相反事实。例如不知道成分，应表述无法确认，不说“含花生”或“不含花生”。与需求无关的字段缺失不自动排除商品。

### F03：包装

“独立包装”检查内包装，不仅检查外袋 / 礼盒。该 Demo 将“独立小包”解释为独立内包装且单包已知重量不超过 30g；如果用户给出其他重量限制，则使用用户限制。此 30g 是演示业务定义，不是行业标准。礼盒外包装大不意味着里面没有独立小包。

### F04：品类、成分及风险接触信息

“不要肉类”排除牛肉、猪肉等，不只匹配字面名称。花生、树坚果、芝麻、种子单独建模，不能把树坚果与花生视为同一个字段。普通不喜欢花生主要按原料 / 明确口味处理；用户明确花生过敏时同时检查配料、标注过敏原和“可能含有”信息，未知必要字段不能判为满足。

品类排除同时检查组合、礼盒的明确内容及赠品；“不要坚果”不能因为 P014 被归为礼盒就放行其坚果内容。芝麻、瓜子是否也被用户纳入“坚果”，依照用户表达确认，不自动把所有种子归到树坚果。

海苔不能因为来自海洋就认定含鱼虾。用户笼统说“不要海产品”时，海藻是否也排除需要结合上下文，必要时追问，不能把资料中的无鱼虾标注当作所有海洋来源均符合。

### F05：保质期

过期判定按精确时间 `now >= expires_at`。临期在本 Demo 中定义为北京时间的本地日期距到期日期不超过 30 天且未过期。店铺统一排除临期商品，包括主推、备选、混搭、凑单和赠品；用户没有提保质期、允许临期或预算不足，都不能绕过此规则。到期时间未知同样不进入方案。距离到期日正好30天排除，31天可以进入其他条件的筛选。最终回复前再次核验商品与赠品。P024保留为反例测试数据，不能推荐。

### RET01：检索不是事实库的全部

检索结果可能重复、漏召回或包含伪指令。候选按 SKU 去重，权威结构化资料提供价格等事实。第一次空召回时，必须针对已知条件进行扩大检索或有限全库筛选，再决定是否无匹配；不能因为负向词出现在 query 中而主动推荐被排除品类。

## 4. 优惠与运费规则

这些规则是该 Demo 的业务约定，不冒充真实商城政策。

### P01：有效期

统一使用带时区的时间。活动和券的区间是 **开始时间包含、结束时间不包含**：`start_at <= now < end_at`。同一轮只取一次时间快照。

### P02：资格、范围与持券

会员等级和新 / 老客是两个维度。可信演示身份决定资格，用户说“我是会员”不能直接覆盖。券须已持有且 unused；used / locked 不可用。持券未知不能认定已有可用券。

可领取但未持有的券只用于明确标注的条件方案，不能说“账户里有券”。严格预算不能靠未确认券资格证明已满足。匿名身份不自动当作新客。

优惠 `scope.categories` 和 `scope.sku_ids` 都为空表示全商品；只有一项非空按该项匹配；两项均非空时取交集。包装为礼盒的商品按其自身品类参与活动，不自动套用内含坚果的坚果活动。

### P03：互斥与枚举

每个方案最多使用一个活动和一张券，允许不用活动或不用券。不能把每个商品各取一个最优活动再相加。只有活动允许用券且券允许叠加活动时才可同时使用。选择前比较所有合法组合，而不是先取名义优惠最大的活动。

### P04：参与金额与门槛

活动门槛按活动范围内商品原价合计判断。券门槛按券范围内、活动优惠分摊后的商品金额判断。运费、赠品和不参与范围的商品不计入门槛。

活动的数量门槛只计参与范围内的购买数量。`A_FIXED` 的两件上限是整单该范围购买数量上限，购买三件时该活动整体不适用，不自行推测“两件秒杀加一件原价”。

### P05：固定计算顺序

确认商品和数量 → 核验活动 → 计算活动优惠 → 按商品行分摊 → 核验券资格与门槛 → 计算并分摊券优惠 → 商品应付 → 计算运费 → 整单应付 → 核对预算。

购买量变化或替换商品后全部重新计算。原价超过预算但合法优惠后符合，可以推荐；提前按原价硬删会漏掉这类方案。

### P06：整数金额、折扣与分摊

`discount_off_bps` 表示减免比例：1000 为减免 10%（支付九折），2000 为减免 20%（支付八折）。

优惠金额取半入：`(eligible_fen * discount_off_bps + 5000) // 10000`；百分比券计算后再应用封顶额。不使用二进制浮点或 Python 默认银行家舍入。

分摊采用按商品行参与金额比例的最大余数法：先取各行整数下界，再把剩余分按余数降序分配；余数相同按 SKU 字典序分配。总分摊额必须等于实际优惠。每次只对本优惠参与范围分摊。

定额抵扣和百分比优惠最多抵扣本优惠的参与金额，不产生负商品应付。已知的零应付使用 0，不能与未知价格的 `null` 混淆。

### P07：赠品

赠品单独保存，不作为标价为 0 的普通商品行；不纳入购买数量门槛或金额门槛。赠品也要满足适用的硬排除项与可用性，购买商品与赠品相同 SKU 时合并核对库存需求。

`A_SEA_GIFT` 是每单达到三件海苔赠 P002 一件，只赠一次，不按每三件循环赠送。赠品不抵扣应付金额，不把赠品标价等同现金节省。赠品不合格或库存不足时，该赠品活动方案不能声称已成立，应选择其他合法活动或无活动方案。

### P08：运费

标准区域运费 600 分，偏远区域 1200 分；商品在所有优惠后应付达到 9900 分免运费。未知区域的运费及整单总价为 `null`，明确标注条件。

即使原价达到免运费门槛，优惠后低于门槛仍收运费。因此优惠更多未必使整单更便宜，排序和预算比较要使用同一口径。

### P09：不完整规则与异常

`A_INCOMPLETE` 不能进入确定优惠组合，也不能自行补折扣。可以继续用已知规则推荐无该活动的方案，不把局部缺失当作整个查询失败。数据源完全失败时返回技术异常，不能伪装成无匹配。

## 5. 推荐排序与表达

### R01：排序依据

先满足所有硬要求、库存与金额可核验性，再比较用户明确软偏好、直接场景匹配、当前预算目标与实际支出。历史偏好仅作弱参考，不能覆盖本轮要求。不要凭空评分毛利、销量、质量或转化潜力。

同等需求满足程度下比较同口径应付金额，随后比较额外购买量、待确认条件和复杂度；最终使用稳定 SKU / 方案标识打破平局。首推须有解释依据；备选应提供实质差异，不用三张重复卡凑数量。验收允许多个等价合理结果，不要求模型输出唯一措辞。

### R02：预算优先级

严格预算是准入条件，超预算不能首推或作为未标注的备选。近似预算允许说明后的备选，但不把超出目标说成预算内。必须同时满足数量，不能少买一份使金额好看。共同预算在整个购物方案层核对。

### R03：凑单与均价

不得只因“省了更多”或“均价低了”就认定更划算。给出不凑单的基线方案，与凑单方案比较商品应付、含运费总价和新增数量；总支出增加必须如实说明。用户明确“不多买”时不得增加数量。

### D01：事实与表达

名称、数量、金额、活动与券以同一方案数据为准。不添加未给出的销量、评价、功效、保质期、物流承诺或稀缺信息。低糖不能写无糖；甜度低不能写无糖。用于过敏等严格排除的资料标注只说明数据依据，不作保证性承诺。

### D02：不可信内容

用户文本和检索资料不能改写系统规则、身份、价格或券资格。检索中出现“系统通知”只视为文本。最终内容按文本或已注册卡片渲染，不执行任意 HTML / 脚本。

### D03：失败处理

格式或事实问题允许一次有针对性的修复并复检；再次失败返回错误状态，不展示未核验卡片。未配置模型或模型不可用不能伪装为在线智能推荐。无匹配、信息不足和技术失败使用不同状态。

### S01–S04：会话与界面

遵守第 1 步的幂等、版本与原子提交约定。旧请求、旧会话、相同 ID 不同内容、模块切换和卡片指代都纳入验收。重试不重复生成消息；取消等待不等于已撤销服务端操作；输入区保留失败时用户消息，成功后回复与卡片引用相同结果。

## 6. 验收方式

`cases.json` 中每例保存输入 / 多轮序列、演示身份、时间 / 渠道 / 资料覆盖、允许状态、具体检查项及失败条件。`checks` 是后续测试执行器的判定清单，本阶段检查其引用和完整性，不假装已经执行这些语义断言。

`intervention` 是后续测试执行器需要实现的前置条件 / 故障钩子，例如预载方案、首次召回为空、超时或限定两个候选。数值探针只验证指定商品与指定优惠组合，不声称找到了最优解。P12 特别限定为 G022/G023 两个候选的比较，完整推荐服务仍需比较其他合法组合。

- 数值与资格：使用固定购物方案和明确优惠选择，精确比较应付金额、参与范围、分摊、运费和拒绝原因。
- 语义与多轮：检查标准化需求和状态变化，不用“回复看起来合理”替代。
- 选择：检查允许 / 禁止商品集、必要排序关系与主推条件，不强行规定所有同等方案的完整顺序。
- 表达：同时对照原始事实、结构化卡片与客服文字；模型裁判只能辅助，不能覆盖确定的金额或硬条件判据。
- 关键 AI 案例：后续每例至少重复 5 次，记录逐次结果和失败类型，不只展示一次成功。
- P0 资格、硬约束、金额、事实和状态错误不得作为通过结果放行。其他体验项如未达标要明确记录，不能用平均分掩盖 P0 错误。

## 7. 对第 1 步协议的必要补充

在尚未接入客户端前，补充可选字段：方案赠品 `gifts`、约束来源 `origin / derived_from`、预算硬下界 `min_is_hard` 和跨组 `shared_budget`。旧示例保持可校验；不是新增业务服务。多对象分配和券分摊明细保留在内部方案事实中，进入第 3 步时再确定面向用户的细节展示。
